# Codex任务指南：DQN诊断与强化实验

**任务背景：** 当前 DQN（warm2 配置）在 budget=1.70 时 forecast_weighted_mae_overall = 0.4179，不仅弱于 Custom PPO（0.3908），甚至弱于 round_robin（0.4032）。理论上，一个正确实现的 DQN 在足够训练步数下不应弱于 round_robin——后者是一个零信息的确定性轮询策略，DQN 只需学会"不比轮询更差"即可超越它。当前失效是**实现层面的结构性问题**，而非 DQN 算法本身的上限。本指南要求 Codex 系统性诊断并修复，最终产出一组可写入论文 Table 2 的 DQN 强化结果。

---

## 一、失效根因诊断（三层，已锁定）

**根因 R1：暖机延迟与 TD 信用分配不匹配。**  
FlowCapt（τ=5步）和 OTT Parsivel²（τ=8步）的暖机延迟意味着"开机"动作的奖励收益要在 5–8 步后才能体现。DQN 的单步 TD 更新（即使使用 3-step return）在 200k steps 内难以将这段延迟奖励正确归因到开机动作。相比之下，PPO 的 GAE（λ=0.95）在 2048 步 rollout 内可以跨越整个暖机窗口进行信用分配。

**根因 R2：候选动作集组合爆炸，缺乏结构化表示。**  
即使 warm2 限制候选到暖机≤2步的传感器（约6个候选），合法子集仍有 10–15 个。DQN 将每个合法子集视为独立离散动作，无法利用动作间的结构相似性（例如"开 sensor 1+2"与"开 sensor 1+3"共享 sensor 1 的贡献）。Custom PPO 的 ActionEmbedding 组件显式建模了这种结构。

**根因 R3：缺乏 oracle-calibrated prior，探索覆盖不足。**  
Custom PPO 通过 oracle-calibrated candidate prior 将初始策略锚定在高质量动作附近，大幅压缩了有效探索空间。DQN 从随机初始化出发，在 200k steps 内的 ε-greedy 探索无法充分覆盖稀疏奖励的高价值区域（尤其是吹雪事件期间的最优传感器组合）。

**关键诊断问题：** warm2 配置（dqn-max-candidate-warmup=2）将候选动作限制为暖机≤2步的传感器，这本意是降低动作空间复杂度，但实际上**剥夺了 DQN 提前开启高暖机传感器的能力**，导致 FlowCapt 和 OTT 几乎永远无法被及时激活，而这两个传感器恰好是吹雪事件期间最关键的测量设备。

## 二、实验修复方案（四个变体，递进式）

以下四个变体按优先级排序。**目标是让至少一个变体的 forecast_weighted_mae_overall 在 budget=1.70 时低于 round_robin（0.4032）**，从而在论文中将 DQN 定位为"有效但次优"而非"无效"。

### 变体 D1：延长训练步数（最低成本，首先尝试）

**修改内容：** 将 `total_timesteps` 从 200k 增加到 **500k**，其余超参数不变（warm2 配置保持）。

**理由：** warm2 配置的动作空间已经足够小（~6候选），主要问题是探索不充分。500k steps 约等于 2.5 倍训练量，对于 6 个候选动作的离散空间应当足够收敛。

**预期效果：** 若 R3（探索不足）是主因，D1 应能将 MAE 降至 round_robin 以下。

**实施步骤：**
```python
# scripts/29_v2_train_dqn.py 或等效训练脚本
# 修改：
total_timesteps = 500_000  # 原为 200_000
# 其余超参数不变
```

**网格实验：** 3 seeds × 3 budgets（1.65/1.70/1.75），warm2 配置，500k steps。

---

### 变体 D2：移除 warm2 限制 + n-step 增大（解除动作空间限制）

**修改内容：**
- 移除 `dqn-max-candidate-warmup=2` 限制，恢复完整候选动作集（所有满足功耗约束的合法子集）
- 将 n-step return 从 3 增加到 **8**（覆盖 OTT 的完整暖机窗口）
- 将 `total_timesteps` 增加到 **500k**

**理由：** warm2 限制虽然减小了动作空间，但同时阻止了 DQN 学习"提前预热高延迟传感器"的策略。n-step=8 可以将 OTT 开机动作的奖励信号直接传播回去，解决 R1。

**注意：** 完整候选集可能有 15–20 个合法子集，DQN 的 Q-head 需要能处理可变大小的动作集。检查 `src/v2/dqn.py` 中的 Q-head 实现是否支持动态动作掩码（masked Q-values）。

**实施步骤：**
```python
# src/v2/dqn.py
n_step = 8  # 原为 3

# scripts/26_v2_grid_experiment.py 或 29_v2_train_dqn.py
# 移除 --dqn-max-candidate-warmup 参数，或设为 None/inf
dqn_max_candidate_warmup = None  # 不限制

total_timesteps = 500_000
```

**网格实验：** 3 seeds × 3 budgets，无 warm2 限制，n-step=8，500k steps。

---

### 变体 D3：引入 Prioritized Experience Replay（PER）

**修改内容：** 在 D1 基础上，将均匀采样 replay buffer 替换为 **Prioritized Experience Replay**（PER，Schaul et al. 2016），优先回放 TD-error 大的转换。

**理由：** 吹雪事件（wind_speed > 8 m/s）在训练数据中是稀疏的（约 20–30% 时步），但这些时步的奖励方差最大（FlowCapt/OTT 的贡献最显著）。均匀采样导致这些高信息量转换被稀释。PER 可以让 DQN 更频繁地从这些关键转换中学习。

**实施步骤：**
```python
# src/v2/dqn.py
# 使用 stable-baselines3 的 PrioritizedReplayBuffer，或手动实现
# 关键参数：
per_alpha = 0.6   # 优先级指数
per_beta = 0.4    # 重要性采样修正（从 0.4 线性增加到 1.0）
per_beta_final = 1.0
buffer_size = 100_000  # PER 通常需要更大 buffer

total_timesteps = 500_000
```

**注意：** 若 stable-baselines3 的 DQN 不原生支持 PER，需要手动实现或使用 `sb3-contrib` 的 `QRDQN`（内置 PER 支持）。

---

### 变体 D4：Oracle-Guided Warm Start（最强修复，对标 Custom PPO 的 prior 机制）

**修改内容：** 在 DQN 训练开始前，用 oracle 的贪心动作选择预填充 replay buffer（**demonstration buffer**），然后再进行正常的 ε-greedy 探索训练。

**理由：** 这是 Custom PPO 的 oracle-calibrated prior 在 DQN 框架下的等价实现。通过预填充高质量转换，DQN 的 Q-network 从一开始就有合理的初始化，避免了从随机策略出发的低效探索阶段。

**实施步骤：**
```python
# scripts/29_v2_train_dqn.py 新增预填充阶段

def prefill_buffer_with_oracle(env, dqn_agent, oracle, n_steps=10_000):
    """用 oracle 贪心动作预填充 replay buffer"""
    obs = env.reset()
    for _ in range(n_steps):
        # 获取 oracle 推荐的贪心动作
        oracle_action = oracle.greedy_action(obs)
        # 执行动作，收集转换
        next_obs, reward, done, info = env.step(oracle_action)
        dqn_agent.replay_buffer.add(obs, next_obs, oracle_action, reward, done)
        obs = next_obs if not done else env.reset()

# 在正式训练前调用
prefill_buffer_with_oracle(env, dqn_agent, oracle, n_steps=10_000)
# 然后正常训练
dqn_agent.learn(total_timesteps=500_000)
```

**注意：** oracle 的 checkpoint 路径为 `checkpoints/oracle_v2_fullopen_balanced/`，需确认接口兼容性。

## 五、论文叙事方案（根据实验结果选择）

### 方案 A：DQN 修复后优于 round_robin（理想情况）

Table 2 中 DQN 行更新为强化后结果，Section 5 描述 DQN 实现细节（包括修复措施），Section 7 Discussion 叙事：

> "The DQN baseline, when trained with extended timesteps (500k) and n-step=8 returns, achieves a forecast-weighted MAE of X at budget=1.70, outperforming round-robin scheduling by Y% but remaining Z% below Custom PPO. This gap is attributable to DQN's lack of structured action representation and oracle-calibrated initialization, both of which are addressed by Custom PPO's five-component design."

### 方案 B：DQN 仍弱于 round_robin（当前现状，接受并解释）

保留当前 warm2 结果，Section 7 Discussion 增加一段结构性解释：

> "The DQN scheduler (warm2 configuration) underperforms round-robin scheduling, a result that warrants explanation. Three structural factors contribute to this outcome. First, the warm-up latencies of FlowCapt (5 steps) and OTT Parsivel² (8 steps) create a temporal credit assignment gap that DQN's 3-step return cannot bridge within 200k training steps; by contrast, PPO's GAE with λ=0.95 spans the full warm-up window within a single 2048-step rollout. Second, the warm2 candidate restriction, while reducing action space size, inadvertently prevents DQN from learning anticipatory activation strategies for high-latency sensors. Third, without an oracle-calibrated prior, DQN's ε-greedy exploration fails to adequately cover the sparse high-reward region corresponding to blowing-snow events. These findings reinforce the motivation for Custom PPO's five-component design and suggest that DQN-based scheduling in this setting would require either substantially longer training or architectural modifications such as prioritized experience replay and demonstration-guided warm-start."

**注意：** 方案 B 在论文中是完全可接受的——它将 DQN 的弱表现转化为对 Custom PPO 设计必要性的正面论证，符合论文的第二层叙事结构（方法贡献层）。
