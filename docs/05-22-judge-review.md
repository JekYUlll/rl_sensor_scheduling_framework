# Review of `05-22-judge.md`

## Verdict

The central decision is correct: the calibrated energy-account diagnostics now support a
storm-window dynamic-advantage claim, while they do not support a full-distribution
dynamic-superiority claim. The cleanest setting is:

- `harvest=0.92`, `capacity=180`, `reserve=20`
- storm-window eval starts: `22943`, `6826`, `21704`, `8183`, `17193`, `16151`
- best overall: `dynamic:snow_core__event_laser_fc4`
- overall oracle loss: `0.4169` vs static snow core `0.4248`
- event oracle loss: `0.3190` vs static snow core `0.3517`
- best dynamic row: `soc_min=48.48`, `energy_guard_dropped=0`, `warmup_abort_count=0`

## Corrections Needed

1. The V3.1 main result should not be described as PD-PPO beating feasible static
   projection. In Table `main_results_v31`, lower is better and static projection is
   better than PD-PPO at `B=1.70` (`0.1597` vs `0.1620`). The correct claim is that
   PD-PPO is the best learned/adaptive policy and remains close to a strong static
   diagnostic reference.

2. The `h=0.94/cap300` failure is not because `h=0.94` exceeds the static-laser
   steady cost. It does not: static laser subsets cost about `1.14--1.16`. The failure
   occurs because the 1024-step eval windows and `capacity=300` allow static laser to
   remain viable despite negative average energy balance.

3. The no-lead `snow_core__event_laser_fc4` cost arithmetic in `05-22-judge.md` is
   off. In the implemented diagnostic, the calm mask is snow core
   (`met+radiometer+surface+snow = 0.82`) and the event mask is
   `met+laser+fc4 = 1.13`. The measured storm-window mean power is about `0.995`
   because the selected storm windows have higher event fractions than the full truth.

4. The current energy account subtracts steady `power_cost`, not `startup_peak_power`.
   Startup peaks are still enforced by the projector as a hard feasibility rail.
   Therefore the capacity explanation should be based on observed SOC/drawdown and
   steady-cost bursts, not on `4 * (startup_peak - harvest)`.

5. `event_flag` is generated by the simulator as `blowing_snow_active`, not observed
   through the scheduled Parsivel/FC4 sensors. It is acceptable for oracle diagnostics
   and stratified evaluation, but an operational controller should replace it with an
   event-probability estimate from always-on meteorological channels.
